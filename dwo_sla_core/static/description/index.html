Enterprise SLA & Escalation Engine for Odoo

Service Level Agreements, Operational Level Agreements and escalation chains — on any model, not just support tickets.

Define commitments once with point-and-click conditions, and let the engine measure, pause, breach and escalate them automatically, in real working hours, with a full audit trail for every decision.

Most SLA tools only watch one kind of record: a helpdesk ticket. Enterprise SLA & Escalation Engine is built differently — it watches any model in your Odoo database. Sales orders stuck in approval, manufacturing orders behind schedule, expense reports awaiting validation, onboarding tasks, vendor commitments: if it is a record in Odoo, you can put a measurable, time-bound commitment on it. Every rule is pure configuration — domain conditions, a target duration and a working calendar — so your implementation team defines new SLAs without writing a line of Python. The engine runs in the background, attaches, pauses, resumes, completes and escalates tasks automatically, and keeps a complete, tamper-evident event log explaining every decision it made. Key Features & Capabilities

Model-Agnostic by Design

Point an SLA Definition at any Odoo model through its six conditions: Start, Stop, Pause, Resume, Cancel and Reset. The engine snapshots the rule when a task attaches, so editing a definition later never changes tasks already running.

Real Working-Hour Calculations

Durations are measured against a working calendar (business hours), not the wall clock — a 4-hour SLA opened Friday at 16:00 does not breach over the weekend. No calendar selected means a straightforward 24/7 clock instead.

SLA and OLA in One Model

Classify each definition as a customer-facing SLA or an internal Operational Level Agreement, optionally tie it to a Vendor for underpinning contracts, and flag it as an officially published Service Commitment for reporting.

Multi-Stage Escalation, Zero Setup

Chain as many percentage thresholds as you need — a 75% warning, a 100% breach notice, a 150% director alert. Each stage emails a responsible person out of the box, or runs a standard Odoo Server Action for custom automation.

Retroactive Start & Pause

Backdate the SLA start to a date already on the record (for example its creation time) instead of the moment the rule was configured, and credit any backdated period that was already on hold — reconstructed from the record's own change history.

Per-Rule Timezone Override

Reuse one working calendar across regions by overriding its timezone per SLA definition, without touching the original calendar or affecting anything else that uses it.

Status On the Record Itself

A single smart button on the ticket, task or any record it watches shows how many SLAs are active and turns red the instant one is breached — no separate screen to check.

How It Works

Six conditions, evaluated by a background job every minute — no polling to configure, nothing to schedule.

1. Define

Pick a model and write the Start Condition, a target duration and, optionally, a working calendar.

2. Attach

The moment a record matches the Start Condition, a task is created and the clock starts — immediately, or retroactively from a date on the record.

3. Track

A background job checks every running task once a minute: pause when the Pause Condition matches, resume when it stops matching, and recompute the deadline against the working calendar.

4. Escalate

Each configured percentage threshold emails the right person once, or runs a custom Server Action — your choice per rule.

5. Close

When the Stop Condition matches, the task closes as Achieved or Breached; the Cancel and Reset conditions handle records that leave scope or change shape mid-flight.

Built for Governed Environments

Two access groups and a complete read-only audit model, so SLA reporting can be opened up without any risk to the underlying rules.

SLA User vs. SLA Manager

Users can read tasks and events to answer “why is this late?”. Only Managers can edit SLA Definitions, trigger a manual re-evaluation or mark an error event resolved.

Every Action Server-Side

Escalation Server Actions always run with the permissions of the background job's own user, never with the permissions of whoever last edited the source record.

Requirements & Installation

Pure configuration, no external services and no library to install — the engine runs entirely inside Odoo on the standard base, resource, web and mail modules.

Retroactive Pause reads the target model's own change-tracking history (mail.thread), so it only has an effect on models and fields that already log changes in Odoo — the configuration screen tells you clearly when that is not the case for a given rule.

The background job runs once a minute as a standard Odoo scheduled action (ir.cron); no cron, queue or worker needs to be set up outside Odoo.

Install

Copy the module into your addons path and install it like any other Odoo app — from the Apps list, or from the command line.

./odoo-bin -d your_database -i dwo_sla_core --stop-after-init

Create your first SLA

Go to SLA → SLA Definitions → New, pick a model, write a Start Condition and a Duration, then save. The next record that matches gets its own SLA Task automatically — no restart needed.

Grant access

Add the users who should only read tasks and events to the SLA / User group, and the users who configure rules to SLA / Manager, from Settings → Users.

Frequently Asked Questions

Does this only work with Helpdesk tickets?

No. An SLA Definition points at any model in your database through its Model field — sales orders, manufacturing orders, project tasks, expense reports, or a fully custom model. Helpdesk needs no special integration.

What happens if I edit a rule while tasks are already running?

Nothing changes for tasks already attached: the duration, calendar and conditions are captured as a snapshot the moment a task attaches. Only new tasks created after the edit use the new configuration.

Can one record have more than one SLA at the same time?

Yes. Create one SLA Definition per commitment — for example a Response SLA and a separate Resolution SLA on the same model — and a record that matches both gets two independent tasks.

How is “breached” decided when there is no working calendar?

With no calendar selected, the engine counts plain 24/7 clock time. With a calendar selected, only working hours count towards the target, so time outside business hours never counts against the deadline.

What does a percentage threshold like 150% actually mean?

100% is the exact deadline. A 150% threshold fires once the task has consumed one and a half times its target duration — useful for a final escalation well after the SLA itself has already breached.

What happens if an escalation action fails?

It is logged once as a failed event with the error message, visible on the Unresolved Error Events screen, so an administrator can fix the configuration. It does not retry automatically.

Is the background processing heavy on the database?

The scheduled job only looks at tasks that are due for a check in the next run and locks each row briefly while it updates it, so it scales with the number of currently active SLAs, not with your whole database.

Can I report on SLA performance without building a dashboard?

Yes. SLA Tasks ship with ready-to-use List, Pivot and Graph views, including an Achieved Rate and a Currently Breaching measure, so you can filter, group and export straight away.
