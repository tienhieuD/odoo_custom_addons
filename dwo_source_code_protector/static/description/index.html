Source Code Protector for Odoo

Ship your Odoo module without shipping its source.

Every module you sell or deploy normally hands over fully readable Python — anyone who installs it can open every file, copy your logic, or rewrite around it. Source Code Protector compiles your business logic to native machine code first, so what you ship still works exactly the same, but can no longer be read as source.

The moment you hand a customer or reseller an Odoo module, you are handing them its source — the pricing rules, algorithms and integrations that took real work to build, in plain readable Python they can open, copy, or quietly rewrite around. Source Code Protector takes your module's raw source, extracts the business logic (models, wizards, reports, controllers), and compiles it to native .so/.pyd binaries with Cython. The methods you protect run exactly as before — often faster, since compiled native code typically outperforms interpreted Python — but can no longer be read, copied or modified as source. What you get back installs and behaves like any other Odoo module, nothing special for your customers to configure.

How It Works

Four steps to a shippable, protected module.

1. Upload the zip

Pick a .zip with one or more Odoo modules, each with its own technical folder name at the top (e.g. my_module/__manifest__.py).

2. Business logic is extracted

Each module's protectable code — models, wizards, reports, controllers — is found by following the real Python import graph, and transformed so it can be compiled.

3. Compiled to native binary

The transformed code is compiled to a native .so/.pyd extension with Cython. It runs exactly as before; it just can't be read as source anymore.

4. Download & ship

Get back a ready-to-ship zip with the same module structure, now protected. Install it on a staging database to confirm, then ship it to your customers.

Import every file explicitly

Standard Odoo convention: every file must be reachable from __init__.py through from . import .... A file nothing imports is invisible to protection, even if Odoo itself still loads it some other way.

# __init__.py
from . import models
from . import wizards

Subclass Odoo base classes directly

Models, wizards and reports must subclass models.Model / TransientModel / AbstractModel directly, not only through your own custom base class defined elsewhere — that indirection is what protection looks for to recognize an Odoo class.

Re-apply @route on every override

If you override a controller method, repeat its @route(...) decorator even if the route itself is unchanged — this is already standard Odoo practice, and it's also how protection recognizes a controller method.

Single underscore, not double

Use one leading underscore for internal methods (_foo). A double leading underscore (__foo) triggers Python's own name-mangling rules and is intentionally left unprotected.

Avoid match/case in protected methods

Python's match/case statement is not yet supported by the compiler used here. An if/elif chain works the same and compiles without issue.

Frequently Asked Questions

Will the protected module still run normally?

Yes — compiled methods behave exactly the same from Odoo's point of view. Always test the protected module on a staging database before shipping it to customers.

Can I run the protected module on a different server?

The compiled .so/.pyd binaries are platform-locked: they only run on a server with the same Python version, OS and CPU architecture as the one that compiled them.

What happens with a module that has nothing to protect?

If no protectable business logic is found (e.g. no models with real methods), that module is marked Skipped with a reason, and the rest of the zip is still processed.

What if my zip has the manifest at its root, with no module folder?

That entry is Skipped with a clear reason: there is no reliable module name to compile against in that shape. Re-zip with the module's technical folder name at the top, e.g. my_module.zip containing my_module/__manifest__.py.

Can I see past protection jobs?

Yes — every upload becomes a job record in Settings → Source Code Protector, with its status, per-module result, and the protected zip to download again.

How long are my uploaded and result files kept?

1 day after the job finishes, after which both are deleted automatically to save disk space. The job's history and per-module results remain.

Do I need anything installed on the server besides this module?

The server needs the jprotect and pyzipper Python packages, and a C compiler with Python headers available for Cython to compile against.
